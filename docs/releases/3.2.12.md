# IBM Verify SDK for Android - Release 3.2.12

## Overview

Version 3.2.12 is a patch release that hardens the browser-based Authorization Code Flow in the Authentication SDK and refreshes build dependencies:

1. **Authorization result delivery hardening** - `OAuthProvider.authorizeWithBrowser` now unregisters its `ActivityResultLauncher` as soon as a result arrives, ignores results delivered after the coroutine has completed, handles a result that is already pending when the launcher is registered, and re-throws `CancellationException`.
2. **`AuthenticationActivity` state restoration** - the activity now persists its authentication state across recreation (for example, process death or configuration change while the browser is open).
3. **New Authentication SDK unit tests** - Robolectric-based JVM tests cover the above fixes.
4. **Dependency updates** - Jackson, Firebase, and Compose Lint Checks versions updated; Robolectric added as a test dependency.
5. **Documentation** - README files corrected to match the current API, install snippets updated to 3.2.12, and version badges now follow the latest GitHub release.

## Breaking Changes

None. This is a backward-compatible release. All existing code targeting 3.2.11 continues to compile and run without modification.

## Bug Fixes

### `OAuthProvider.authorizeWithBrowser` - launcher lifecycle and cancellation

**Updated:** [`OAuthProvider`](../../sdk/authentication/src/main/java/com/ibm/security/verifysdk/authentication/api/OAuthProvider.kt)

Four issues in `authorizeWithBrowser` were fixed:

- **Launcher unregistered on result.** The `ActivityResultLauncher` registered with `activityResultRegistry` is now unregistered as the first action in the result callback. Previously it was only unregistered when the coroutine was cancelled, so a registered callback could outlive the request.
- **Late results ignored.** If the continuation is no longer active when a result is delivered (for example, a second delivery for the same launcher), the callback returns without attempting to resume it. This prevents `IllegalStateException: Already resumed` crashes.
- **Pending result during registration.** `ActivityResultRegistry` replays an already-pending result synchronously from `register()` (for example, after the host activity was recreated). The callback now tolerates running before the launcher reference is assigned, and when it has already resumed the continuation the browser is not launched again. Without this the call failed with `UninitializedPropertyAccessException`.
- **`CancellationException` propagation.** An explicit `catch (e: CancellationException) { throw e }` guard now precedes the broad `catch (e: Throwable)` handler, so coroutine cancellation is no longer converted to `Result.failure(CancellationException)`. This is consistent with the hardening applied to other network-facing methods in 3.2.10.

### `AuthenticationActivity` - state restored after recreation

**Updated:** [`AuthenticationActivity`](../../sdk/authentication/src/main/java/com/ibm/security/verifysdk/authentication/AuthenticationActivity.kt)

`AuthenticationActivity` previously reset `hasAuthenticationStarted` and `code` in `onCreate` on every creation. If Android recreated the activity while the browser was in the foreground, the activity treated the recreation as a fresh start and could launch a second Custom Tab or lose the authorization code.

The activity now saves both values in `onSaveInstanceState` and restores them in `onCreate` when `savedInstanceState` is non-null. A fresh launch (no saved state) behaves exactly as before.

## Test Coverage

### New tests

| File | New tests | What they cover |
|---|---|---|
| [`AuthorizeWithBrowserTest`](../../sdk/authentication/src/test/java/com/ibm/security/verifysdk/authentication/AuthorizeWithBrowserTest.kt) | 4 | Launcher unregistered after the first result and a duplicate delivery is ignored; a result pending during `register()` completes the call without launching the browser; `CancellationException` re-thrown when the calling coroutine is cancelled; `AuthenticationActivity` saves and restores state across recreation |

These are JVM unit tests that run under Robolectric (`@Config(sdk = [34])`), so they do not require a device or emulator.

`sdk/authentication/build.gradle.kts` gained the following test dependencies: `kotlinx.coroutines.test`, `mockito.kotlin`, and `robolectric`.

## Documentation

The module READMEs, `TOC.md` and example READMEs were reviewed against the source and corrected. No SDK behaviour changed.

- **Accurate code samples.** Samples in the Authentication, Core, MFA and FIDO2 READMEs now match the current API.
- **Current install instructions.** All snippets reference 3.2.12 and the JitPack coordinates; the FIDO2 README no longer points at a local Maven repository.
- **Correct requirements and dependencies.** Minimum API level is 29 everywhere, and the Adaptive module is documented as standalone (no dependency on Core).
- **Version badges.** README badges now show the latest GitHub release automatically, so they no longer need a manual update per release.
- **Navigation.** Broken links and anchors were fixed, `TOC.md` was rebuilt, and the DPoP demo, the SSL certificate bypass guide and the example apps are now cross-referenced.

## Upgrade Notes

No code changes are required when upgrading from 3.2.11 to 3.2.12.

## Known Issues

`OnPremiseAuthenticatorService.nextTransaction` contains debug-level `log.error(…)` calls used during active development. These will be replaced with `log.debug(…)` in a subsequent patch.
